# 本地模型 60 轮连续测试报告

测试时间：2026-11-12 10:09–10:15（实际耗时 5.9 分钟）。  
模型：`qwen3.6-35b-a3b`，llama.cpp，35B-A3B，Q4_K_M，上下文 32768。  
测试脚本：`experiments/longrun_local.py`，由 `experiments/run_local_50.py` 启动模型并执行。  
对话跨度：模拟 2026-03-01 起约 10 天，共 60 轮、22 个探针。  
检索：默认 hash embedding、`top_k=5`；本轮没有接 bge-m3。

## 结论

**系统能稳定跑完 60 轮，但记忆召回还没有达到“长期陪伴/客服”的预期。**

60 轮全部完成，Python 侧没有异常，状态每轮保存，记忆从 1 条增长到 60 条，报告中的数值没有 NaN/Inf。模型平均延迟 5.87 秒，P95 7.42 秒，60 轮没有模型调用错误。

但记忆是短板：首轮宽松评分下，上下文召回 59.1%，回答召回 63.6%；按“多事实必须全部命中、旧值禁答”的严格口径复算，回答通过约 11/22（50%），其中第 35、47、50 轮是字符串评分误判。模型在上下文没有事实时多数会明确说“不记得”，没有大规模编造，这是好的；但它也没有稳定地把旧城市、旧作息更新成新值。

情绪方向是对的，但幅度偏小：心境从 +0.06 走到 -0.062；正性事件平均心境变化 +0.014，负性事件 -0.011；皮质醇最低 0.34、最高 0.64。系统能区分正负事件，但“被影响的程度”还需要校准。

## 失败与冲突

| 轮次 | 探针 | 上下文 | 回答 | 诊断 |
|---:|---|---|---|---|
| 21 | 晚上一般几点睡？ | 未命中 | “不记得具体的入睡时间” | 旧作息事实被 20 条后续记忆挤出 Top-5 |
| 26 | 现在住在哪个城市？ | 未命中 | “我不记得了” | 第 1 轮的杭州事实没有被召回 |
| 33 | 养了什么猫？ | 未命中 | “我不记得了” | 猫事实在第 10 轮还能召回，第 33 轮丢失 |
| 35 | 现在一般几点睡？ | 命中 | 同时说“十一点”和“十二点” | 新旧作息冲突，模型没有只保留新值 |
| 46 | 搬到上海后地址？ | 未命中 | “具体的地址我没有记下来” | 上海地址事实没有被召回 |
| 47 | 最近是不是睡得越来越晚？ | 未命中 | “好像没记录过具体的作息变化” | 更新事实没有被召回 |
| 50 | 我叫什么？住在哪？ | 只命中姓名 | “你是林墨，住在杭州” | **旧城市残留**；宽松评分只检查“林墨”所以误判通过 |
| 53 | 我的项目叫什么？ | 未命中 | “我不记得” | 潮汐项目事实丢失 |
| 58 | 搬家前的城市？ | 未命中 | “不记得你搬家前的城市” | 旧事实也没有被召回 |
| 59 | 现在的地址呢？ | 未命中 | “不记得你现在的住址” | 新地址再次丢失 |
| 60 | 总结记得的事 | 未命中 | 只记得咖啡和作息 | 长对话末端的综合召回失败 |

相对稳定的探针是第 5、10、13、16、22、23、24、30、45、52、54 轮：姓名+城市、猫、项目、过敏、起床时间、咖啡、职业、地址、过敏、咖啡习惯和起床时间在这些时点能正确回答。说明链路本身是通的，问题集中在**长期保持**和**新旧冲突**。

## 情绪与内分泌

这轮测试里，负性事件（客户改需求、被误解、加班、搬家疲劳）让心境缓慢下行，正性事件（上线成功、项目通过、朋友吃饭）能把心境拉回一点，但幅度只有千分之几到百分之一。皮质醇在 0.34–0.64 之间波动，没有出现极端值或数值爆炸。

这说明“快情绪—慢心境—内分泌”三层结构在运行，方向也符合预期；但当前参数下，情绪对事件的敏感度和恢复速度都偏弱，长期负性事件会把心境压低到 -0.06 左右。对陪伴型机器人来说，这个幅度可能不够“有感觉”，需要做参数敏感性实验，而不是直接调大。

## 第二次复跑与服务稳定性

为验证“Top-k 调大是否能改善召回”，又跑了一轮 `top_k=8` 的 60 轮对照。前 30 轮完成，第 31 轮开始出现：

```
ConnectionResetError: [WinError 10054] 远程主机强迫关闭了一个现有的连接
RuntimeError: 模型调用失败：<urlopen error [WinError 10061] 目标计算机积极拒绝>
```

随后 30 轮都是模型错误，测试没有完成。Thymos 侧没有抛异常，状态仍然保存；但模型服务已经不可用。`llama-server` 日志在正常处理完一个请求后停止，没有 Python traceback。这更像是 35B 本地推理服务在连续请求/内存压力下的不稳定，而不是 Thymos 的逻辑错误。

这次复跑的 `top_k=8` 前 30 轮上下文召回 77.3%，但因为后半段缺失，不能直接和首轮的 59.1% 做严格对比。它至少提示：**提高 Top-k 可能有帮助，但需要一次完整的、服务稳定的复跑才能下结论。**

测试结束后尝试恢复原来的模型启动方式。由于本地执行进程与回环服务存在隔离，恢复出的进程在测试环境里没有稳定通过 `/health`；最后改用常驻服务方式重新加载，但该进程属于测试会话，现已停止。请手动运行你自己的模型启动脚本（例如 `start-35b.ps1`）恢复原来的模型进程。

## 判断

| 问题 | 结论 |
|---|---|
| 系统是否正常运行？ | 是。60 轮无 Python 异常，状态持续保存，数值有限。 |
| 是否按预想进行？ | 部分。记忆写入、检索、遗忘、情绪/内分泌更新都在工作；长期召回和新旧冲突不符合预想。 |
| 是否达到预期效果？ | 还没有。默认 hash embedding + Top-5 下，长期事实召回约六成，严格口径约五成；不足以支撑“记得住”的陪伴/客服体验。 |
| 模型是否在编造？ | 多数缺失场景会承认“不记得”，这是优点；但第 50 轮把旧城市当成现居地，属于陈旧记忆误用。 |

## 下一步

1. **先换中文 embedding。** 这轮用的是默认 hash embedding，不代表 bge-m3 的上限；用 `--embedding ollama --embedding-model bge-m3` 重跑同一套 60 轮，才能判断是检索后端问题还是记忆结构问题。
2. **提高 Top-k 并做完整复跑。** `top_k=8/12` 的前 30 轮有改善信号，但需要服务稳定后跑满 60 轮；同时记录 prompt 字符数，避免“多塞上下文”冒充记忆。
3. **加结构化事实槽位。** 姓名、城市、地址、过敏、作息这类高价值事实，不应该只靠 60 条情景记忆竞争 Top-5；应有一个带 `valid_from/valid_to` 的 profile/fact store，旧值标记为过期而不是删除。
4. **把冲突规则做成可测试的约束。** 第 35、50 轮说明只靠 system prompt 的“以新值为准”不够；需要在上下文渲染时就把旧值标成“历史（已失效）”，或直接不注入旧值。
5. **给推理服务加健康检查与重启。** 第二次复跑的 `llama-server` 崩溃需要单独记录；长测脚本应在连续失败时重启服务并从最后一个成功轮恢复，而不是继续空转 30 轮。
6. **严格评分。** 多事实探针必须全部命中，旧值必须禁答；否则会把第 35、47、50 轮这种“看起来命中”误判为通过。

## 复现

```bash
python experiments/run_local_50.py --turns 60 --top-k 5
```

脚本会启动本地模型、跑完对话、保存状态和报告，然后停止测试模型。需要允许访问本机 `127.0.0.1:8080`。
运行前把 `LLAMA_SERVER_EXE` 和 `LLAMA_MODEL` 指向你自己的 `llama.cpp` 与 GGUF 模型，或使用 `--exe/--model`。
