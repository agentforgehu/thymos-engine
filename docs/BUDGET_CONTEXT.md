# 小上下文预算下的记忆增强：50 轮 A/B 实测

## 为什么做这一轮

本地模型的上下文长度通常比云端模型小。把最近几十轮对话全部塞进 prompt，会挤占推理空间，而且并不能保证模型真的“记住”早期事实：早期内容会被截断，旧值和新值还会同时出现。

这一轮不再增加上下文，而是反过来：**把记忆块限制在 600 / 900 字符，用结构化事实和有效期冲突处理，让更少的内容承载更关键的信息。** 目标不是让模型读得更多，而是让它在读得少的时候仍然答得对。

## 这次改了什么

`FactStore` 负责保存“当前为真”的高价值事实：姓名、城市、地址、宠物、过敏、项目、截止日期、职业、朋友、睡眠、起床、咖啡偏好。每个事实带 `valid_from` / `valid_to`；当用户给出新值时，旧值被关闭而不是删除，因此既能回答“现在”，也能在明确问“以前”时回答历史。

`Thymos.render_context(..., query, max_chars)` 现在按硬预算渲染：结构化事实优先，剩余空间才给紧凑的情景记忆；被新事实取代的旧情景记忆会被过滤，避免“杭州”和“上海”、“十一点”和“十二点”同时出现。`AgentMemory.context(..., max_chars=900)` 是这一能力的门面接口。

## 测试设计

同一套 50 轮脚本、同一个本地模型 `qwen3.6-35b-a3b`、同一段 system prompt，只改变记忆块：

| 条件 | 记忆块来源 | 预算 |
|---|---|---:|
| `thymos` | 结构化事实 + 预算内情景记忆 | 600 / 900 字符 |
| `recent` | 最近用户/助手对话，按时间倒序截断 | 600 / 900 字符 |

脚本包含 16 个探针，覆盖姓名、城市、宠物、项目、截止日期、过敏、作息、职业、地址、搬家前后城市等。每个探针分别记录“上下文里有没有事实”和“模型回答有没有答对”，避免把模型的失败和记忆系统的失败混在一起。

## 结果

| 指标 | `thymos` | `recent` | 差异 |
|---|---:|---:|---:|
| 完成轮数 | 50 / 50 | 50 / 50 | — |
| 模型错误 | 0 | 0 | — |
| 探针数 | 16 | 16 | — |
| 上下文召回 | **100%** | 50.0% | +50.0 pp |
| 回答召回 | **100%** | 43.8% | +56.2 pp |
| 平均记忆块字符 | **487.9** | 713.5 | 少 225.6 |
| 平均延迟 | 5.76 s | 6.17 s | 少 0.41 s |

### 600 字符档

把预算再压到 600 字符后，`thymos` 仍然是 16/16，平均记忆块 417.5 字符；`recent` 的回答召回仍是 43.8%，平均记忆块 490.5 字符。

| 600 字符档 | `thymos` | `recent` | 差异 |
|---|---:|---:|---:|
| 完成轮数 | 50 / 50 | 50 / 50 | — |
| 模型错误 | 0 | 0 | — |
| 上下文召回 | **100%** | 37.5% | +62.5 pp |
| 回答召回 | **100%** | 43.8% | +56.2 pp |
| 平均记忆块字符 | **417.5** | 490.5 | 少 73.0 |
| 平均延迟 | 5.60 s | 5.25 s | 多 0.35 s |

关键点不是“Thymos 赢了”，而是它在**平均只用 418–488 字符**的情况下，比平均 490–714 字符的最近对话基线答对更多。结构化事实把“姓名、城市、宠物、项目、过敏、地址、作息”压缩成了十几行，不需要占用大量上下文。

两档测试的所有记忆块都没有超预算：900 档 `thymos` 最大 580 字符，600 档最大 463 字符；`recent` 最大分别为 888 和 593。

逐探针看，`thymos` 16 个全对：姓名与城市、猫的名字和品种、项目与交付日、花生过敏、十一点睡、七点起、咖啡不加糖、独立开发者、搬家前当前城市杭州、搬家后上海徐汇、十二点后睡、最后总结都答对。`recent` 只有前 5 个探针（姓名城市、猫、项目、过敏）和较早的作息、地址、趋势等 7 个答对；第 22、23、24、26、33、45、46、50 轮都出现“我不记得”，第 35 轮虽然上下文里有“十二点后”，但仍被旧的“十一点前”带偏，回答成“争取十一点前入睡”。

历史查询（例如“搬家前住哪”）不在本次 16 个探针里，由 `tests/test_facts.py` 和 `tests/test_context_budget.py` 单独覆盖；本次 50 轮只测“当前事实是否被正确保持/切换”。

第 26 轮曾暴露一个真实问题：脚本里“考虑搬去上海 / 如果搬去上海”被误当成真实搬迁，导致城市提前改写。修复后只有“决定搬 / 已经搬 / 下周搬”或后续地址陈述才更新城市；同时新增了“搬家意向不覆盖当前城市”的回归测试。修复后同一套 50 轮达到 16/16。

## 这说明什么

第一，限制上下文时，**记忆的表示方式比记忆的数量更重要**。把原始对话截断到 600/900 字符，只能留下最近几轮；把同样预算换成结构化事实，早期关键事实仍然在。

第二，**新旧冲突必须在记忆层解决，而不是靠 prompt 让模型“以新值为准”**。`recent` 的第 35 轮就是反例：旧值和新值都在上下文里，模型会同时引用。`thymos` 把旧值关闭、把旧情景过滤掉，当前事实只剩一个。

第三，`context_ok` 和 `answer_ok` 必须分开看。`recent` 的上下文召回是 50%，回答召回只有 43.8%：有一次事实在上下文里，模型仍然答错。这说明“检索到了”不等于“用对了”。

## 边界

这是一次**小规模、合成脚本、单模型**的工程验证，不是对人类记忆的测量，也不是通用 benchmark。16 个探针、600/900 字符预算、规则抽取、hash embedding，这些条件都限制了结论的外推。事实抽取目前只覆盖中文的高价值句式；更复杂的转述、否定、条件和多跳事实还需要 LLM 抽取或更强的语义检索。

另外，`recent` 基线本身也会受到模型生成质量影响；第 35 轮的“上下文有、回答错”说明仅靠 substring 评分也会低估或高估某些回答。后续应加入人工复核和更细的语义评分。

## 怎么用

```python
from thymos import AgentMemory

memory = AgentMemory(".thymos/bot.json")
context = memory.context(user_text, top_k=5, max_chars=900)
reply = llm(context, user_text)
memory.observe(user_text)
```

`max_chars` 是硬预算，不是建议值。对更小的模型可以从 600 或 400 开始；先保证事实块，再让情景记忆使用剩余空间。

复现同一套 600 字符对照：

先把 `LLAMA_SERVER_EXE` 和 `LLAMA_MODEL` 指向你自己的 `llama.cpp` 构建与 GGUF 模型；也可以用 `--exe/--model` 覆盖。

```bash
python experiments/run_local_50.py \
  --script experiments/budget_compare.py \
  --script-args "--max-chars 600 --modes thymos,recent" \
  --turns 50
```
