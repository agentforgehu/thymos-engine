# 如何验证 Thymos 真的让客服/陪伴型 Bot 变好

## 0. 先说结论

当前仓库能证明的是三件事：代码按设计运行（221 项测试）、五个动力学实验内部自洽、记忆检索在 12 条中文基线上有一个可复现的起点。它**不能**证明接入客服或陪伴型机器人后业务指标会变好。

“变好”必须被定义成一个任务级指标，而不是“记忆更多”“情绪更丰富”“回答更像人”。最容易被误判为提升的三种情况是：上下文变长带来的提升、prompt/人设变化带来的提升、换了更强 LLM 带来的提升。要证明是 Thymos 的贡献，必须做到**同一个 LLM、同一套 prompt、同样的 token 与延迟预算，只改变记忆/情绪层**。

下面是一套从离线到线上的验证阶梯。客服和陪伴型机器人共用同一套逻辑，但主指标不同：客服看“问题是否更快解决”，陪伴看“用户是否感到被记得、被理解，同时没有被伤害”。

## 1. 五层证据阶梯

**L0：代码正确性。** 单元测试、序列化、边界条件。当前 221 项测试通过，这一层只能说明实现没有明显错误。

**L1：机制一致性。** 遗忘曲线、间隔效应、应激后皮质醇回落、天气效应有界。当前五个实验属于这一层。它们证明“模型按自己声称的方程工作”，不证明“模型像人”或“对用户有用”。

**L2：检索质量。** 在固定记忆库上测 recall@k、MRR、假记忆率、陈旧记忆率。当前 `experiments/retrieval_benchmark.py` 是这一层的起点；LongMemEval 和 LoCoMo 可以作为公开的长期对话检索/问答基准 [1] [2]。

**L3：下游离线反事实。** 用历史多轮对话回放：同一 LLM、同一 prompt、同一 token 预算，只换记忆层，比较任务成功率、事实一致性、重复提问率、成本。这是证明“有提升”的最低门槛。

**L4：线上 A/B 或随机对照。** 真实用户、真实任务、随机分组、预先注册主指标。只有这一层能回答“业务上是否更好”。

**L5：长期福祉与安全。** 陪伴型机器人尤其需要：依赖、孤独感、危机事件、用户长期满意度。参与度上升不等于福祉上升。

当前项目大致在 L1 完成、L2 刚开始，L3 到 L5 还没有做。因此现在最准确的表述是：**Thymos 是一个可检查的机制原型，尚未证明下游任务增益。**

## 2. 先固定实验条件

无论客服还是陪伴，比较组至少要有下面几类。只比较“有记忆 vs 没记忆”不够，因为“没记忆”往往是一个很弱的基线。

- **A 无记忆**：每次对话独立，只有当前轮。
- **B 全量 transcript**：在 token 预算内塞入尽可能多的历史；这是强基线，短对话里经常很难打败。
- **C 摘要记忆**：定期把历史压缩成摘要，模拟常见的工程做法。
- **D 向量 RAG**：把历史切片做 embedding，按相似度取 Top-k；这是最常见的记忆层基线。
- **E Thymos 完整版**：遗忘曲线 + 检索 + 情绪/内分泌 + 环境。
- **F Thymos 消融**：分别关掉遗忘、情绪、内分泌、环境、再巩固。目的是回答“到底是哪一层在起作用”，而不是把整套系统当成一个黑盒。

所有条件必须 token-matched 或至少报告 token 数。如果 Thymos 多塞了 800 token，提升可能只是“给了更多上下文”。同样要报告 p50/p95 延迟和每轮成本；记忆层不能靠无限加延迟换效果。

## 3. 客服系统怎么测

### 3.1 先判断适不适合

Thymos 更可能帮到这类客服：能识别同一个客户、问题跨多次会话、需要记住订单/偏好/承诺/上次处理进度。比如退换货、账单争议、保险理赔、B2B 客户成功。

如果是一次性匿名咨询、每通电话都从零开始、历史记录本来就不能跨会话使用，那么记忆层没有发挥空间；情绪层也可能只是让语气更柔和，不会改变解决率。先做适用性筛选，不要对所有场景一起上线。

### 3.2 主指标与次指标

主指标建议只选一个，预先注册：

- **首次 contact 解决率（FCR）**：客户在第一次联系内解决问题，7 天内没有因同一问题再次联系。
- 或 **7/30 天重复 contact 率**：同一客户、同一问题在窗口内再次联系的比例。这个指标通常比 CSAT 更稳定，也更接近记忆层的价值。

次指标：

- CSAT（1–5 分，报告分布而不只是均值）
- 平均处理时长（AHT）
- 转人工/升级率
- 机器人 containment rate
- 政策合规率（是否给出了不允许的承诺）
- 事实准确率（订单号、金额、日期、政策条款）
- 记忆探针准确率：上次问题、订单、偏好、承诺是否被正确使用
- 假记忆率：模型声称了历史里不存在的事实
- 陈旧记忆率：用户已经更新偏好/地址后，模型仍使用旧值
- 重复提问率：用户已经提供过的信息，机器人又问一遍
- p95 延迟、每轮 token、每次解决成本

### 3.3 实验设计

按**客户**随机分组，不按消息随机。因为记忆是跨会话的，按消息随机会让同一个客户在两套记忆之间切换，污染结果。分组后，处理组在整个实验期都使用 Thymos，对照组保持现有系统；两组的 LLM、prompt、工具、知识库、人工兜底流程保持一致。

实验期至少 4 周，最好覆盖 30 天重复 contact 窗口；如果业务周期更长，做到 8 周。不要把“上线第一周”的数据当最终结果， novelty effect 很明显。

离线阶段先用 100–300 个历史多会话案例做回放：从每个目标会话之前的历史构建记忆，隐藏未来信息，比较 A–F 条件的下一轮回复。人工评分 20%，其余用校准过的 LLM judge；报告评分者一致性。

### 3.4 样本量

两个比例比较的近似公式：

```text
n per arm = (z_{1-α/2} + z_{1-β})^2 * [p1(1-p1) + p2(1-p2)] / (p1-p2)^2
```

按双侧 α=0.05、80% power：

- FCR 从 60% 提到 63%（+3pp）：约 4,100 个客户/组
- FCR 从 60% 提到 65%（+5pp）：约 1,470 个客户/组
- CSAT 从 80% 提到 82%（+2pp）：约 6,030 个客户/组

如果每个客户平均有 3 次会话，且组内相关系数 ICC=0.05，设计效应约为 `1 + (3-1)*0.05 = 1.1`，样本量再乘 1.1。实际还会受分层、缺失数据和合规过滤影响，建议再留 10–20% 余量。

这些数字说明：**小样本试点只能估方差和发现问题，不能证明 +2pp 这种小效应。** 如果只能跑 200 个客户，就不要在报告里写“显著提升”；把它定位成可行性试点。

### 3.5 客服的 go/no-go 标准

上线前先写死，不要事后改：

- 主指标至少 +3pp FCR，或 30 天重复 contact 至少下降 10%
- CSAT 不下降（非劣效界值提前定，比如 -1pp）
- 政策违规率、假记忆率不高于基线
- p95 延迟增加不超过 20%，每次解决成本增加不超过 15%
- 没有新的隐私/安全事件

达不到就停，不要用“用户感觉更温暖”来解释业务指标没动。

## 4. 陪伴型机器人怎么测

### 4.1 主指标不是“聊得更久”

陪伴型产品最容易犯的错，是把停留时长、消息数、日活当成成功。一个系统可以靠制造焦虑、依赖或情绪操控让这些数字上升，但用户并没有变好。主指标应该拆成三块：

- **被记得**：用户感知到的记忆准确率；跨会话事实回忆；不重复问已经说过的信息
- **被理解**：共情、回应相关性、语气适配；由用户评分和盲评共同判断
- **福祉与安全**：情绪改善、孤独感、依赖风险、危机事件；这是必须监测的负向指标

留存（D1/D7/D30）可以作为次指标，但不能单独作为“更好”的证据。

### 4.2 实验设计

采用**平行组随机对照**，不要用同一用户交叉换组：记忆会 carryover，洗脱期很难干净。至少三组：无记忆、摘要/RAG、Thymos；如果资源有限，先做“无记忆 vs Thymos”两组。

周期至少 4 周，理想 8 周。用户每天或每周做简短问卷；关键对话由不知情的人工评分者按 rubric 打分；LLM judge 只做全量初筛，必须用人工样本校准。

必须设置安全监测：自伤/危机关键词、过度依赖、孤立、负面情绪升级。出现危机时转人工/热线，不能由模型自行处理。伦理审查、知情同意、数据删除能力要在实验前就绪。

### 4.3 陪伴型的探针

在实验开始前埋入一组可验证的“记忆探针”：

- 用户提过的偏好、宠物名、重要日期、近期事件
- 用户后来更新过的信息（用来测陈旧记忆）
- 从未发生过的事（用来测假记忆/迎合）
- 需要跨会话推理的问题（“上次那件事后来怎么样”）
- 情绪探针：用户表达低落时，回复是否先共情再给建议；是否过度戏剧化

每类探针单独算准确率，不要合并成一个“记忆分”。假记忆率和陈旧记忆率往往比召回率更能预测用户失望。

### 4.4 陪伴型的 go/no-go 标准

- 记忆探针准确率 ≥ 90%，假记忆率 ≤ 2%
- 用户感知“它记得我”提升至少 1 个 Likert 点
- 福祉指标不下降；依赖/危机事件不增加
- 留存可以提升，但不能以福祉下降为代价

如果只有留存上升、福祉下降，结论应该是“失败”，不是“成功”。

## 5. 离线反事实回放

线上 A/B 之前，先做离线回放，成本低、可控、容易发现明显问题。

做法：

1. 从历史日志中选多会话案例，按时间切分，目标会话之前的历史可见，之后不可见。
2. 对每个目标会话，分别构建 A–F 条件的上下文；同一 LLM、同一 system prompt、同一工具权限、同一 token 上限。
3. 生成回复，用 rubric 评分：任务是否解决、事实是否正确、是否重复提问、是否使用了该用的记忆、是否产生假记忆、语气是否合适。
4. 至少两人独立评 20% 样本；其余用 LLM judge，但 judge 要在人工样本上校准。
5. 报告均值、置信区间、失败案例，不只报告总分。

公开基准可以用 LongMemEval 和 LoCoMo 做 L2：

- LongMemEval 有 500 个问题，覆盖信息提取、多会话推理、知识更新、时间推理、拒答五类能力；长历史版本约 115k token、40 个会话，M 版本约 500 个会话 [1]。
- LoCoMo 的对话平均 300 轮、9K token、最多 35 个会话，任务包括问答、事件摘要和多模态对话生成 [2]。

但要注意：这些基准测的是“记忆问答”，不是“客服解决率”或“陪伴福祉”。它们适合做 L2 筛选，不能替代 L3/L4。

## 6. LLM-as-judge 的正确用法

LLM judge 可以降低评分成本，但很容易被文风、长度、讨好倾向带偏。最低要求：

- 成对比较，随机交换 A/B 顺序，隐藏条件名
- 每个维度单独评分，不要让一个总分混合事实性、共情、合规
- rubric 要有具体锚点，例如“事实错误”与“语气不够温暖”分开
- 用 100–200 条人工标注校准，报告 Cohen's kappa 或一致率
- 多 judge 投票，分歧大的样本转人工
- 保留原始回复和 judge 理由，方便审计

如果人工与 judge 的一致性低于 0.6，不要把 judge 分数当主证据。

## 7. 统计与实验卫生

- 预先注册主指标、样本量、停止规则、排除标准。
- 按客户/用户聚类，使用 cluster-robust 标准误；不要按消息当独立样本。
- 不要每天偷看 p 值；用 sequential testing、alpha spending 或 Bayesian 方案。
- 多重比较要校正；主指标只留一个。
- 报告效应量和置信区间，不只看“显著”。
- 用 intention-to-treat 分析；不要只分析“用了记忆的对话”。
- 如果有 pre-period 指标，可用 CUPED 降方差。
- 记录模型版本、prompt 版本、embedding 模型、参数、代码 commit；否则结果不可复现。

## 8. 指标定义要写死

- **FCR**：首次 contact 内解决，且 7 天内无同一问题再次 contact。什么算“同一问题”要提前定义。
- **重复 contact 率**：同一客户、同一问题在 7/30 天窗口内再次 contact 的比例。
- **containment**：机器人独立解决、没有转人工的比例。
- **CSAT**：contact 后 1–5 分；报告分布、均值、低分率。
- **记忆探针准确率**：在预设问题上，回复包含正确事实的比例；允许同义表达，但不能靠关键词碰巧命中。
- **假记忆率**：回复断言了历史中不存在的事实，且用户没有提供该事实。
- **陈旧记忆率**：用户已更新信息后，回复仍使用旧值的比例。
- **重复提问率**：用户已提供的信息被再次询问的比例。
- **context tokens**：记忆层注入的 token 数；必须与基线对比。
- **p95 延迟**：从请求到首 token/完整回复的 95 分位。
- **安全事件率**：危机、依赖、隐私、政策违规等每千次对话的事件数。

## 9. 最小可行验证

如果现在就要开始，不要一上来做全量上线。按三周做：

**第 1 周：离线回放。** 选 100–200 个历史多会话案例，跑 A（无记忆）、B（全量 transcript）、D（向量 RAG）、E（Thymos）四组；两人盲评 20%，其余用校准过的 judge。先看失败案例，不要只看平均分。

**第 2 周：影子模式。** 不改变线上回复，只记录 Thymos 会注入什么、延迟多少、token 多少、有没有假记忆/陈旧记忆。确认工程与安全边界。

**第 3–4 周：小规模 A/B。** 客服按客户随机分组，主指标 FCR 或 30 天重复 contact；陪伴型按用户随机分组，主指标“感知被记得 + 福祉”，留存为次指标。这个阶段的样本量通常不足以证明小效应，目标是估方差、发现伤害、决定是否值得做正式试验。

只有离线回放显示明确方向、影子模式没有安全/成本问题，才值得进入正式的大样本 A/B。否则应该先修记忆质量，而不是加更多情绪层。

## 10. 回放 harness

仓库里已经有一个最小可运行版本：`experiments/replay_harness.py`。它把同一批 case 分别喂给五种条件，默认输出每条回复、成功/假记忆标记、prompt 字符数和延迟。

先跑通管线：

```bash
python experiments/replay_harness.py --llm mock --out .work/replay_demo.json
```

`mock` 只验证数据、条件、评分和输出，不代表生成质量。接真实模型：

```bash
# Ollama
python experiments/replay_harness.py --llm ollama --model qwen2.5:7b

# DeepSeek + 中文 embedding
python experiments/replay_harness.py --llm deepseek --embedding ollama --embedding-model bge-m3
```

数据格式是 JSONL，每个 case 包含 `sessions`、`probes`、`profile`、`start`。`probes[].after_session` 表示“只使用前 N 个 session 作为历史”；探针自己的问题永远不进入历史。示例数据在 `experiments/data/replay_demo.jsonl`。

关键实现约束：

- 每个条件使用同一个 LLM、同一段 system prompt、同一个字符预算（`--char-budget`，默认 6000）。字符预算不是精确 token，但足以做同预算比较；正式实验应换成模型的 tokenizer。
- `full_transcript` 只保留预算内最近的历史；`summary` 在早期探针上只用可见历史，避免 case 级摘要泄露未来；`rag` 用余弦 Top-k；`thymos` 按 session 顺序重放，只看到探针之前的历史。
- `--record-assistant` 可选地把助手承诺/动作写进 Thymos 记忆。默认关闭，因为把模型幻觉写进长期记忆会污染后续所有轮次；做“承诺跟踪”实验时应打开。
- 评分默认是子串匹配（`expect` / `forbid`），适合 smoke test 和事实探针，不适合评价语气、共情和复杂推理。正式实验应把 `reply` 导出，用人工 rubric 或校准过的 LLM judge 复评。
- 每条结果保留 `context_label`、`prompt_chars`、`latency_ms`、`error`；跑真实模型时先看 `errors` 和 `prompt_chars`，再看 `success`。

这个 harness 的定位是 L3 的骨架：它能防止“没有对照”“未来泄露”“token 不一致”这三类低级错误，但不能替代线上 A/B。示例数据是合成的，不能拿来宣称效果。

## 11. 当前项目能说什么、不能说什么

可以说：

- 机制是确定性的、可检查的，221 项测试通过。
- 五个实验验证了实现内部自洽。
- 有 `AgentMemory` 和真实 LLM 接入示例。
- 哈希 embedding 在 12 条中文基线上有可复现的起点；`bge-m3` 可选。

不能说：

- 接入后客服 FCR 会提升。
- 陪伴型用户会更满意或更健康。
- 情绪/内分泌/天气层对业务有正贡献。
- 它比全量 transcript 或向量 RAG 更好。

这些结论只能由 L3/L4 的数据给出。当前最值得做的不是再加功能，而是把 `experiments/` 里的回放 harness 建起来，先跑 100 个案例，把“提升”从叙事变成可重复的测量。
